## Contexto: cómo resuelve nombres una computadora

1. Toda máquina tiene un **resolver** (proceso/librería del SO que sabe
   resolver nombres) y un archivo tipo `resolv.conf` con la entrada
   `nameserver <IP>`.
2. El resolver primero revisa su **caché** local:
   - Si tiene el registro → responde al navegador, pero marcado como
     **no autoritativo** (no viene directo de la fuente).
   - Si no lo tiene → consulta al servidor DNS externo configurado
     (ej. `8.8.8.8`).
3. DNS corre sobre **UDP puerto 53**, es decir, sobre un protocolo de
   transporte **no confiable** (best-effort, sin garantía de entrega).
4. Se puede observar el tiempo de resolución DNS en el navegador, pestaña
   *Network* → *Timing* de una petición.

## Arquitectura del proyecto: DNS Interceptor

Idea general: reemplazar el `nameserver` del resolver de la máquina cliente
por un **DNS Interceptor** propio, de forma transparente (el navegador y el
resolver no deben notar el cambio). Es el mismo principio detrás de
servicios como **Route 53** de AWS, aplicado a pequeña escala.

Componentes:

- **Cliente DNS**: la máquina normal, sin cambios salvo apuntar su
  `nameserver` al interceptor.
- **DNS Interceptor**: contenedor Docker con una aplicación en **Rust**
  escuchando en **UDP/53**. Recibe los paquetes DNS y decide qué hacer con
  ellos.
- **DNS API**: componente REST (Java) al que el interceptor reenvía las
  consultas que no puede resolver localmente.

Nota práctica: el puerto UDP/53 suele estar protegido por antivirus,
firewalls del SO y software de seguridad — hay que investigar cómo
levantarlo igual (parte del ejercicio de investigación).

## Formato del mensaje DNS (RFC 1035, sección de header)

El header del mensaje DNS es binario (usa bytes sin representación gráfica
ASCII), de longitud fija, y entre otros campos incluye:

- **ID**: 2 bytes, identificador de la transacción.
- Byte siguiente incluye, de más significativo a menos significativo:
  - **QR** (1 bit): `0` = query, `1` = respuesta.
  - **OPCODE** (4 bits): tipo de consulta. `0` = *standard query*
    (existen otros valores como *inverse query*, etc.).
  - Resto de banderas (AA, TC, RD, ...).

**Regla de procesamiento que pide el proyecto:**

- Se extrae el **tercer byte** del header del paquete recibido.
- Se examina el **bit más significativo** → ese es **QR**.
  - Si `QR = 0` → es una consulta (query), se sigue examinando.
  - Si `QR ≠ 0` → no se procesa nada especial con ese paquete.
- Se examinan los siguientes 4 bits → **OPCODE**.
  - Si `QR = 0` **y** `OPCODE = 0` → es un **query estándar**: se debe
    examinar en detalle e identificar el host que se está resolviendo
    (esta parte queda pendiente de profundizar en la siguiente clase).
  - Si el paquete **no** es un query estándar (`QR` u `OPCODE` distinto de
    lo esperado):
    1. Codificar la solicitud completa en **Base64**.
    2. Enviarla por **HTTP(S) POST** al endpoint del componente **DNS API**.
    3. La respuesta llega también codificada en Base64.
    4. Decodificarla y devolverla al cliente que hizo la consulta original.

## Por qué Base64 aquí (idea clave del curso)

- DNS es un protocolo **binario**: usa bytes sin representación gráfica en
  ASCII.
- HTTP es un protocolo de **texto plano**: solo transporta caracteres
  imprimibles.
- Para meter un mensaje binario dentro de un protocolo de texto, se
  **codifica en Base64** (convierte bytes arbitrarios a un alfabeto de
  caracteres imprimibles). Prácticamente todo lenguaje trae Base64 en su
  librería estándar.
- Consecuencia interesante del diseño: se está transportando
  - un protocolo **no confiable (UDP/DNS)** sobre uno confiable (**TCP**
    dentro de HTTP), y
  - un protocolo con **caracteres no imprimibles** sobre uno que solo
    acepta **caracteres imprimibles** (HTTP/Base64).
- Todo esto debe pasar desapercibido para el cliente final: ni el resolver
  ni el navegador deben notar que hay un interceptor en medio. Por eso es
  crítico leer bien el RFC y no equivocarse de bit al armar/parsear el
  header.
